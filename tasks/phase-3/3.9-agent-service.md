# Step 3.9 — Agent Service

## Goal

Create a **provider-neutral `AgentService`** that orchestrates a single bounded
turn between the LLM layer and the existing tool infrastructure:

LLM response → optional tool call proposal → `ToolExecutor` → tool result →
next LLM step (bounded).

This step adds application orchestration only. It does not add OpenAI-specific
tool-calling wire formats into the generic agent layer.

## Existing Context

Already implemented and must be reused:

- `LLMProvider` protocol + `OpenAIProvider` + provider factory
- provider-agnostic `LLMService`
- `ToolDefinition` (`backend/app/tools/schema.py`)
- `ToolRegistry` / `ToolBinding` (`backend/app/tools/registry.py`)
- `ToolValidator` (`backend/app/tools/validation.py`)
- `ToolExecutor` / `ToolExecutionResult` (`backend/app/tools/execution.py`)
- `CharacterTools` + `character_tool_bindings()` as the first concrete tools

Confirmed non-goals already deferred:

- OpenAI Responses API tool-calling integration belongs with provider adapters,
  not inside generic AgentService contracts
- Permissions / GM-player authorization are later

## In Scope

- Introduce `AgentService` (or equivalent) in the services layer
- Accept a user/system prompt turn and optional tool registry/executor wiring
- Define a small provider-neutral agent result/turn contract
- Bound tool-calling behavior (max steps / explicit stop conditions)
- Use `ToolExecutor.execute(tool_name, arguments)` for all tool invocations
- Unit tests with fake/stub LLM provider (no network)

## Out of Scope

- Phase 4 story entities (Campaign/Scene/NPC)
- Maps / tokens
- Multiplayer
- SaaS / auth / billing
- HTTP endpoint unless a later roadmap step explicitly requires it
- Broad autonomous loops without a hard bound
- Changing ToolRegistry / ToolValidator / ToolExecutor public contracts
  unless a tiny compatibility fix is objectively required
- Marking other roadmap steps complete

## Required Interfaces

Prefer a minimal public surface such as:

```python
class AgentService:
    def __init__(
        self,
        llm_service: LLMService,
        tool_executor: ToolExecutor,
        # optional: tool definitions exposure helper
    ) -> None: ...

    def run_turn(self, ...) -> AgentTurnResult: ...
```

Exact method names may vary, but must remain:

- provider-neutral
- free of OpenAI request/response field names in the generic contract
- dependent on `ToolExecutor` rather than calling handlers directly

## Acceptance Criteria

1. `AgentService` exists and is importable from the services package.
2. A turn can complete with **no tools** (plain LLM text response).
3. A turn can execute **exactly one** registered tool via `ToolExecutor` when
   the model proposes a valid tool call (simulated via stub provider).
4. Invalid tool proposals (unknown tool / bad args) become controlled tool
   failure results and do not crash the service.
5. Unexpected tool/internal exceptions are not swallowed by a bare
   `except Exception` inside AgentService.
6. No imports of `CharacterTools`, `CharacterRepository`, FastAPI, or Settings
   inside the generic AgentService module.
7. No OpenAI SDK imports inside the generic AgentService module.
8. Character tools continue to work when registered through the existing
   binding helpers and executed through `ToolExecutor`.
9. Full suite remains green; new focused agent tests are added.
10. Architecture checks still pass.

## Required Tests

Create `tests/test_agent_service.py` (name may vary) covering at least:

- no-tool turn success
- one valid tool call routed through ToolExecutor
- tool validation failure does not invoke handler
- expected tool handler failure returns controlled result to the agent turn
- unexpected exception from executor/handler propagates
- AgentService module has no OpenAI/Character/FastAPI imports
- max-step / bound behavior stops further tool calls

Use stub/fake LLM provider objects; no network.

## Architecture Constraints

- Generic agent orchestration must not become OpenAI-specific.
- Tool invocation path: Agent → ToolExecutor → Registry binding handler.
- Do not call `binding.handler` from AgentService directly.
- Do not re-implement validation inside AgentService.
- Preserve dependency direction from `.cursor/rules/ai-tools.mdc`.
