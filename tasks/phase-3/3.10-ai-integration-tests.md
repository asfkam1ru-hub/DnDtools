# Step 3.10 — AI Integration Tests

## Goal

Close Phase 3 by completing the **production OpenAI → tool execution path** and
proving it with offline integration tests.

After this step, a real composed stack can run:

```
OpenAI model response
  → vendor-specific adapter (OpenAIAgentModel)
  → provider-neutral AgentModelResponse / ToolCallProposal
  → AgentService
  → ToolExecutor
  → CharacterTools
  → persistence
```

Phase 3 must not be marked complete while the only functioning tool-calling
path is test-only `ScriptedAgentModel`.

Success = smallest appropriate production OpenAI structured-tool adapter +
deterministic offline integration suite (injected fake OpenAI client; no live
network; no API key required in CI).

## In Scope

### Production (smallest appropriate adapter)

Implement a vendor-specific **`OpenAIAgentModel`** that implements the existing
`AgentModel` protocol and owns all OpenAI wire-format concerns:

1. Accept `Settings` + injectable OpenAI client (same injection pattern as
   `OpenAIProvider`).
2. Implement `complete(messages, *, tools=None) -> AgentModelResponse`.
3. When `tools` is provided/non-empty:
   - translate `Sequence[ToolDefinition]` → OpenAI Responses tool schema
     (explicit helper at adapter boundary);
   - call `client.responses.create(...)` with model, input/messages, and tools.
4. Parse structured OpenAI tool-call output → `ToolCallProposal(name, arguments)`
   (explicit helper; arguments as parsed JSON object, not raw string left to
   AgentService).
5. Parse plain-text assistant output → `AgentModelResponse(content=..., tool_call=None)`.
6. Preserve existing **`OpenAIProvider.generate(prompt) -> str`** behavior and
   its tests unchanged (text-only path remains available via `LLMService`).

### Minimal compatible refactor (allowed only if required for dependency direction)

If `OpenAIAgentModel` cannot live under `providers/` without importing
orchestration from `AgentService`, extract neutral agent contracts to a small
shared module (e.g. `backend/app/agent/contracts.py`):

- `AgentMessage`, `ToolCallProposal`, `AgentModelResponse`, `AgentModel` Protocol

`backend/app/services/agent.py` re-exports these types; **AgentService behavior
unchanged**. This is a move-only refactor, not a redesign.

Preferred layout after audit:

| Module | Responsibility |
| --- | --- |
| `backend/app/agent/contracts.py` (new, if needed) | provider-neutral agent step types |
| `backend/app/providers/openai_agent_model.py` (new) | OpenAI Responses adapter implementing `AgentModel` |
| `backend/app/providers/factory.py` (extend) | `create_openai_agent_model(settings, client=...)` |
| `backend/app/services/agent.py` | unchanged orchestration; optional re-exports |

Do **not** add OpenAI SDK imports to `AgentService`, `ToolExecutor`, or generic
tool modules.

### Offline integration tests

Add focused integration tests composing real production modules with injected
fake OpenAI client responses (no network).

Minimum scenarios listed under **Required Tests**.

### Wiring note (not a new loop)

`AgentService` already bounds tool steps via `max_tool_steps`. The new adapter
implements **one model step per `complete()` call**; AgentService remains the
only loop owner.

Recommended production composition for tool-capable turns:

```python
model = create_openai_agent_model(settings, client=client)
agent = AgentService(llm_service, tool_executor, model=model, max_tool_steps=...)
```

Default `model=None` (text-only `LLMServiceAgentModel`) remains valid and tested.

| Direction | Function (name may vary) | Input → Output |
| --- | --- | --- |
| Outbound | `tool_definitions_to_openai_tools` | `ToolDefinition[]` → OpenAI Responses `tools` payload |

## Acceptance Criteria

1. **`OpenAIAgentModel` exists** and implements `AgentModel` without importing
   `AgentService`, `ToolExecutor`, `CharacterTools`, or FastAPI.
2. **Text-only OpenAI response** via `OpenAIAgentModel.complete(..., tools=None)`
   (or empty tools) returns `AgentModelResponse` with `tool_call=None`.
3. **One OpenAI tool proposal** flows through:
   `OpenAIAgentModel` → `AgentService` → `ToolExecutor` → Character persistence
   → subsequent model step → final assistant text in `AgentTurnResult`.
4. **Tool definitions are translated** and passed to `responses.create` when
   tools are supplied (asserted in unit test against mock client call kwargs).
5. **Structured OpenAI tool-call response** is translated to `ToolCallProposal`
   with parsed arguments; AgentService passes them to `ToolExecutor.execute`.
6. **Tool arguments are validated** by existing `ToolValidator` (invalid args →
   controlled `ToolExecutionResult.success=False`; handler not called).
7. **Unknown tool** proposal → controlled validation failure surfaced back into
   the agent transcript; turn completes without crash.
8. **Unexpected handler exception** (e.g. `RuntimeError`) propagates through
   `AgentService`; not swallowed by adapter or agent.
9. **Multiple model/tool steps** respect `max_tool_steps` (existing AgentService
   behavior; integration test proves end-to-end with fake multi-response client).
10. **`OpenAIProvider.generate` unchanged**; existing tests still pass.
11. **`AgentService` unchanged** in orchestration semantics (only optional
    contract re-export move allowed).
12. **No live network / API key** required for new tests or CI.
13. **`make audit` green**.
14. ROADMAP `3.10` remains unchecked until human review after implementation.

## Architecture Constraints

- **AgentService stays provider-neutral** — no OpenAI SDK, no Responses field
  names in its public contracts.
- **Tool stack stays vendor-neutral** — no OpenAI imports in registry/validation/
  execution/schema/character modules.
- **OpenAI wire-format translation stays in the adapter** (`OpenAIAgentModel` +
  private helpers); do not push vendor shapes into AgentService.
- **Dependency direction:**
  ```
  OpenAIAgentModel (providers) → agent contracts + ToolDefinition + Settings + OpenAI SDK
  AgentService (services) → agent contracts + ToolExecutor (no OpenAI)
  ToolExecutor → registry/validator (no OpenAI, no AgentService)
  ```
  Adapters may depend on neutral contracts and schemas; generic layers must not
  depend on OpenAI or Character concrete tools.
- **Tool invocation path:** AgentService → ToolExecutor only.
- **No `except Exception`** at adapter/agent boundaries for expected failures;
  unexpected errors propagate.
- **No unbounded loop** — one `complete()` per AgentService iteration;
  `max_tool_steps` enforced by AgentService.

## Proposed production design (implementation guide)

Smallest clean design after auditing current contracts:

1. **`OpenAIAgentModel`** in `backend/app/providers/openai_agent_model.py`
   implements existing `AgentModel.complete`.
2. **Neutral types** live in `backend/app/agent/contracts.py` if needed so the
   adapter does not import `AgentService`.
3. **`create_openai_agent_model`** added to `backend/app/providers/factory.py`.
4. **`OpenAIProvider.generate`** left as-is for plain text via `LLMService`.
5. **AgentService** unchanged; OpenAI tool turns pass
   `model=create_openai_agent_model(...)`.
6. Adapter translates:
   - `AgentMessage` transcript → OpenAI Responses `input` format
   - `ToolDefinition.parameters` → OpenAI function/tool parameter schema
   - OpenAI output function/tool call item → `ToolCallProposal`
