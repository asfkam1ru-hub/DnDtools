# Step 4.4 — Character Persistence Refactor

## Goal

Migrate SQLAlchemy models and repositories from monolithic `CharacterRecord`
to generic character storage plus per-system profile records (D&D first).

Support zero profiles, migrated legacy rows, and
`UNIQUE(character_id, game_system_id)`.

## Existing Context

- `CharacterRecord` stores identity + D&D columns in one `characters` table.
- `CharacterRepository` maps directly to legacy `Character` domain model.
- Domain split contracts exist after 4.2 / 4.3.
- Bridge functions may map legacy ↔ split during migration.

## In Scope

- New generic character table / record (identity + ownership + lifecycle metadata)
- New D&D profile table linked by `character_id`
- `CharacterSystemProfile` persistence (or embedded relation metadata as designed)
- Repository CRUD: character with 0, 1, or N profiles
- Data migration for existing SQLite rows → generic + one D&D profile each
- DB-level `UNIQUE(character_id, game_system_id)`
- Removing last profile does not delete the Character
- Repository-focused tests

## Out of Scope

- HTTP/API shape changes (4.5)
- CharacterTools changes (4.6)
- Lifecycle list/filter API behavior (4.7)
- Export/import payloads (4.8)
- User / Campaign persistence

## Required Interfaces

Repository layer should support at minimum:

```python
# Generic character CRUD
create_character(generic: GenericCharacter) -> GenericCharacter
get_character(character_id: UUID) -> GenericCharacter | None
update_character(generic: GenericCharacter) -> GenericCharacter | None
delete_character(character_id: UUID) -> bool

# Profile CRUD (D&D first)
create_dnd_profile(character_id: UUID, profile: DndCharacterProfile) -> ...
get_dnd_profile(character_id: UUID) -> DndCharacterProfile | None
update_dnd_profile(...) -> ...
delete_dnd_profile(character_id: UUID) -> bool  # keeps Character
list_characters(...) -> ...  # may evolve in 4.7 for lifecycle filters
```

Exact naming may vary; behavior must match acceptance criteria.

## Data/Persistence impact

- Split columns: identity → generic table; D&D columns → profile table
- Existing rows migrate to generic + one DND profile (via bridge)
- New characters may persist with zero profiles
- Enforce uniqueness per game system per character

## Acceptance Criteria

1. Persistence reflects target split model.
2. Migrated legacy data round-trips through repository + bridge without data loss
   for representable fields.
3. Zero-profile character can be created and retrieved.
4. Duplicate D&D profile for same character rejected at DB/repository layer.
5. Deleting last profile leaves Character row intact.
6. Repository tests green; full suite green.
7. Temporary dual-read or one-shot migration strategy documented if used.

## Required Tests

- Repository CRUD for generic character with 0 and 1 profiles
- Migrated legacy data round-trip
- Duplicate profile rejected
- Remove last profile keeps Character
- Use temporary SQLite (deterministic, offline)

## Architecture Constraints

- Persistence imports domain types; domain must not import SQLAlchemy.
- Do not change generic AI tooling.
