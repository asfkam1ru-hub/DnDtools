## 1. Current architecture snapshot

### 1.1 Runtime stack (what actually executes today)

All live request and tool paths use the **Stage 2 monolithic Character**:

```
HTTP (main.py)
  → CharacterCreate / CharacterUpdate / CharacterResponse (schemas/character.py)
  → app.models.character.Character (monolith: identity + D&D sheet)
  → CharacterRepository → CharacterRecord (single SQLite table)

AgentService → ToolExecutor → CharacterTools
  → same Character monolith + CharacterRepository
```

| Layer | File | Current role |
| --- | --- | --- |
| Legacy domain | `backend/app/models/character.py` | **Primary runtime domain** — `id`, `name`, D&D fields combined |
| API schemas | `backend/app/schemas/character.py` | Mirrors monolith; `CharacterResponse` subclasses legacy `Character` |
| Persistence ORM | `backend/app/persistence/models.py` | `CharacterRecord` — one table, all columns |
| Repository | `backend/app/persistence/repository.py` | CRUD maps `CharacterRecord` ↔ legacy `Character` |
| HTTP | `backend/app/main.py` | `/characters` CRUD on monolith |
| AI entity tools | `backend/app/tools/character.py` | Five tools; schemas embed D&D fields in create/update |
| Errors | `backend/app/errors.py` | Character-specific 404/422 contracts (stable) |

**Not wired into runtime:** `backend/app/domain/*`, `backend/app/game_systems/dnd/*`.

### 1.2 Uncommitted target-domain layer (not yet primary)

Parallel contracts exist in the worktree but are **imported only by domain tests**:

```

  generic_character.py      GenericCharacter (owner_id, lifecycle, narrative fields)

```

## 3. Exact Character → SystemProfile migration delta

### 3.1 Target base Character (`GenericCharacter`)

| Field | Legacy `Character` today | Target |
| --- | --- | --- |
| `id` | yes | **KEEP** on base |
| `owner_id` | **missing** | **ADD** (required UUID reference) |
| `name` | yes | **KEEP** on base |
| `description` | missing | **ADD** (default `""`) |
| `biography` | missing | **ADD** |
| `personality` | missing | **ADD** |
| `notes` | missing | **ADD** |
| `avatar` | missing | **ADD** |
| `appearance` | missing | **ADD** |
| `lifecycle_state` | missing | **ADD** (`ACTIVE` default) |
| `created_at` / `updated_at` | missing | **ADD** |
| `race`, `class_name`, `level` | on monolith | **MOVE** → DndCharacterProfile |
| `hp`, `max_hp` | on monolith | **MOVE** → DndCharacterProfile |
| ability scores (6) | on monolith | **MOVE** → DndCharacterProfile |
| `inventory`, `skills` | on monolith | **MOVE** → DndCharacterProfile |

### 3.2 Platform relation (`CharacterSystemProfile`)

| Invariant | Today | Target |
| --- | --- | --- |
| Links character to game system | N/A | `id`, `character_id`, `game_system_id` |
| Stores mechanics | N/A | **No** — mechanics in profile payload |
| Uniqueness | N/A | `UNIQUE(character_id, game_system_id)` at persistence |
| Zero profiles | N/A | Valid — Character exists without profiles |

### 3.3 D&D profile (`DndCharacterProfile`)

All mechanic fields from legacy `Character` except `id` and `name`. Validation
rules preserved: level 1–20, abilities 1–30, hp ≤ max_hp.

Canonical system key: `DND_GAME_SYSTEM_ID = GameSystemId("dnd")`.

### 3.4 Bridge limitation (temporary)

- `split_legacy_character(legacy, *, owner_id)` — owner must be supplied explicitly.
- `merge_legacy_character(generic, dnd)` — drops `owner_id`; legacy model cannot represent it.
- Bridge maps only fields representable on legacy `Character`; narrative/lifecycle
  fields on `GenericCharacter` are lost on merge (expected until legacy retired).

## 5. Dependency order for 4.2–4.10

### 5.1 Recommended order (confirmed safe)

```
4.2 Base Character Domain Refactor
  → 4.3 D&D Character Profile Extraction
  → 4.4 Character Persistence Refactor
  → 4.5 Character API and Schemas Alignment
  → 4.6 Character Tools Alignment
  → 4.7 Character Lifecycle Alignment
  → 4.8 Character Import / Export
  → 4.9 Existing Character Tests Migration
  → 4.10 Core Alignment Integration Tests
```

### 5.2 Rationale

| Dependency | Why |
| --- | --- |
| 4.2 before 4.3 | Base identity/ownership must be stable before treating D&D as attached profile; bridge already assumes this split. |
| 4.3 before 4.4 | Persistence needs both table shapes; D&D validation rules finalized on profile type. |
| 4.4 before 4.5–4.6 | HTTP and tools must read/write split storage. |
| 4.5 before 4.6 (soft) | Stable API semantics help define tool compatibility; tools could follow 4.4 alone if API shim deferred — prefer 4.5 first. |
| 4.7 after 4.4–4.5 | Lifecycle persists on base Character and affects list endpoints. |
| 4.8 after 4.4+ | Export/import needs stable stored shapes. |
| 4.9 after 4.5–4.6 | Migrate tests once runtime paths exist. |
| 4.10 last | Proves full stack; adds architecture guards. |

### 5.3 Note on existing worktree

Domain contracts for 4.2 and 4.3 largely exist **in parallel** to the monolith.
Remaining 4.2/4.3 work is **integration**: make split types primary and retire
monolith usage — not re-invent contracts from scratch.

**No alternate order required** based on current code inspection.
