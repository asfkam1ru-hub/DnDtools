# Step 4.8 — Character Import / Export

## Goal

Provide a versioned export/import payload for generic Character plus all system
profiles, with safe ID handling on import.

Foundation only — not full product UI.

## Existing Context

- Split domain + persistence + API (4.2–4.5) define storable shapes.
- Import must never trust external IDs as persistence primary keys.

## In Scope

- Export payload shape including base Character + profile list
- Import validation + create-new-Character-with-new-IDs behavior
- Domain or service-level import/export functions (HTTP optional if in scope of 4.5 patterns)
- Focused unit tests

## Out of Scope

- Clone operation (duplicate with new identity is import, not clone shortcut)
- Campaign bundle export
- Pathfinder profiles
- User ownership reassignment logic beyond neutral `owner_id` passthrough rules

## Required Interfaces

Target payload shape:

```json
{
  "schema_version": "1",
  "character": {},
  "system_profiles": []
}
```

Import always generates new internal UUIDs for Character and profiles.

## Data/Persistence impact

Reads/writes via 4.4 repository; no new tables required unless versioning metadata needed.

## Acceptance Criteria

1. Export includes base Character + all attached profiles.
2. Import validates structure and schema version.
3. Import creates new Character + new profile IDs (never reuses imported ids).
4. D&D profile content preserved on import/export round-trip (new ids).
5. Tests green; full suite green.

## Required Tests

- Export structure for character with 0 and 1 profiles
- Import generates new IDs
- Imported payload IDs not reused as persistence keys
- Invalid payload rejected predictably

## Architecture Constraints

- Import/export logic may live in application/domain service layer.
- Do not embed import in generic AI tooling unless explicitly scoped later.

See `docs/DEFINITION_OF_DONE.md` + human review before ROADMAP `4.8` checkbox.
