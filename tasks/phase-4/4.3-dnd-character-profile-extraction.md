# Step 4.3 — D&D Character Profile Extraction

## Goal

Extract all D&D-specific character mechanics into `DndCharacterProfile` under
`backend/app/game_systems/dnd/`, linked to base Character via
`CharacterSystemProfile` + `DND_GAME_SYSTEM_ID`.

Preserve existing validated D&D behavior (ability bounds, hp ≤ max_hp, level
1–20, inventory/skills) while keeping base Character system-independent.

## Existing Context

- Legacy `app.models.character.Character` embeds D&D fields on the monolith.
- Partial `DndCharacterProfile` and legacy split/merge bridge may exist in the
  worktree — see [4.1-current-core-delta-audit.md](4.1-current-core-delta-audit.md).
- Base Character domain contracts are defined in 4.2.
- Runtime persistence, API, and tools still read/write the monolith.

## In Scope

- Complete `DndCharacterProfile` with validation parity to legacy Character
- Temporary `split_legacy_character` / `merge_legacy_character` bridge (if still
  needed until 4.4–4.6 migrate runtime paths)
- Bridge contract: explicit `owner_id` on split; merge drops `owner_id`
- Unit tests for D&D validation + bridge round-trip for legacy-representable fields
- Document bridge as temporary (removable in 4.9 / 4.10)

## Out of Scope

- Persistence tables for profiles (4.4)
- HTTP/API exposure of split models (4.5)
- CharacterTools schema/handler changes (4.6)
- Pathfinder or other game systems
- Modifying generic AI infrastructure

## Required Interfaces

```python
class DndCharacterProfile(BaseModel):
    race: str
    class_name: str
    level: int  # 1..20
    max_hp: int
    hp: int
    inventory: list[str]
    skills: list[str]
    strength: int  # 1..30
    dexterity: int
    constitution: int
    intelligence: int
    wisdom: int
    charisma: int

def split_legacy_character(
    legacy: Character,
    *,
    owner_id: UUID,
) -> tuple[GenericCharacter, DndCharacterProfile]: ...

def merge_legacy_character(
    generic: GenericCharacter,
    dnd: DndCharacterProfile,
) -> Character: ...  # drops owner_id — legacy limitation
```

## Data/Persistence impact

None in this step. Bridge maps between legacy monolith and split domain types
only. Profile storage is 4.4.

## Acceptance Criteria

1. All D&D mechanic fields live on `DndCharacterProfile`, not `GenericCharacter`.
2. D&D validation rules match legacy Character behavior.
3. `split_legacy_character` requires explicit `owner_id`; never invents ownership.
4. `merge_legacy_character` round-trips all legacy-representable fields; omits
   `owner_id` on legacy model.
5. `DND_GAME_SYSTEM_ID` is the canonical key for D&D profile relation.
6. No persistence/API/tool production files changed beyond domain + bridge scope.
7. Full suite green.

## Required Tests

`tests/test_character_domain_boundaries.py` (or successor):

- D&D validation parity (hp ≤ max_hp, level bounds, ability bounds)
- split → merge round-trip equals original legacy Character payload
- split propagates explicit `owner_id`; merge drops it
- `name` on GenericCharacter only, not on DndCharacterProfile

## Architecture Constraints

- `game_systems/dnd/` may import `domain` types; must not import HTTP/tools.
- `domain` must not import `game_systems` except via explicit bridge module.
- Do not bypass ToolExecutor or alter AI layers.
